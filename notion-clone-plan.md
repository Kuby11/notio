# Notion-clone (portfolio project): план по этапам + стартовый промпт

## Ключевые архитектурные решения

| Область             | Выбор                                                                     | Почему                                                                   |
| ------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Монорепо            | pnpm workspaces + Turborepo                                               | общие пакеты, кеш сборок                                                 |
| Frontend            | Next.js (App Router), TanStack Query, Zustand, Zod, shadcn/ui             | запрошенный стек                                                         |
| Редактор блоков     | Tiptap (ProseMirror) или BlockNote, dnd-kit для drag&drop                 | не изобретать редактор с нуля                                            |
| Backend             | **Hono** на Cloudflare Workers                                            | нативно для Workers, Hono RPC даёт end-to-end типы                       |
| Микросервисы        | Workers + **Service Bindings** (RPC между воркерами)                      | без HTTP-оверхеда и публичных внутренних эндпоинтов                      |
| БД                  | Cloudflare D1, **своя база на каждый сервис** (database-per-service)      | настоящая изоляция микросервисов                                         |
| Файлы               | Cloudflare R2 (presigned/прямая загрузка)                                 |                                                                          |
| Доп. инфраструктура | KV (кеш/сессии), Queues (фоновые задачи), Durable Objects (realtime)      | показывает знание экосистемы                                             |
| ORM / миграции      | **Drizzle ORM** + drizzle-kit (D1) во всех сервисах                       | типобезопасно, миграции в репозитории                                    |
| Аутентификация      | **Better Auth** (Drizzle-адаптер, D1) в auth-service                      | не писать криптографию самому; сессии, OAuth, 2FA, rate limit из коробки |
| Realtime            | Durable Objects + Yjs (CRDT)                                              | групповое редактирование без конфликтов                                  |
| Тесты               | Vitest, @cloudflare/vitest-pool-workers, Testing Library, MSW, Playwright |                                                                          |
| CI/CD               | GitHub Actions + Wrangler                                                 |                                                                          |

### Микросервисы

1. **gateway** — единственная публичная точка входа: CORS, rate limit, проверка JWT, маршрутизация в сервисы через Service Bindings, агрегация OpenAPI.
2. **auth-service** — **Better Auth** + Drizzle-адаптер + D1: email/пароль, OAuth (GitHub/Google), сессии, email-верификация, опционально 2FA; KV как secondary storage для сессий и rate limit. Через JWT/JWKS-плагин публикует публичные ключи, чтобы gateway и сервисы проверяли токены локально.
3. **workspace-service** — рабочие пространства, участники, роли (owner/editor/viewer), приглашения.
4. **pages-service** — страницы (дерево), блоки, версии/история, избранное, корзина (soft delete).
5. **media-service** — загрузка файлов/обложек/иконок в R2, метаданные в D1, подписанные URL.
6. **search-service** — полнотекстовый поиск (D1 FTS5), индексация по событиям из Queues.
7. **realtime-service** (обязательный) — Durable Objects: один DO на страницу (комната), WebSocket с Hibernation API, Yjs-синхронизация документа, presence (курсоры, кто онлайн), периодический снапшот в pages-service. Токен проверяется при апгрейде соединения, роль (viewer = только чтение) проверяется на каждое сообщение.

Общие пакеты: `packages/contracts` (Zod-схемы + типы событий), `packages/db` (общие утилиты Drizzle), `packages/config` (tsconfig/eslint), `packages/ui` (при необходимости).

## Этапы разработки

### Этап 0. Фундамент (1–2 дня)

- Монорепо (pnpm + Turborepo), TypeScript strict, ESLint, Prettier, husky + lint-staged, commitlint.
- `apps/web`, `services/*`, `packages/*`; базовый CI (lint, typecheck, test).
- Wrangler-конфиги, локальный запуск всех воркеров одной командой (`pnpm dev`).
- ADR-документы (`docs/adr/`) для ключевых решений.
- **Готово, когда:** пустой gateway отвечает `/health`, фронт его вызывает, CI зелёный.

### Этап 1. Контракты и инфраструктура бэкенда (2–3 дня)

- `packages/contracts`: Zod-схемы для User, Workspace, Page, Block, File; единый формат ошибок (RFC 7807).
- Gateway: роутинг в сервисы по Service Bindings, request-id, логирование, rate limit (KV).
- Drizzle + миграции D1 для каждого сервиса, сиды.
- **Тесты:** unit для схем, интеграционные для gateway (vitest-pool-workers).

### Этап 2. Auth и пользователи (2–3 дня)

- auth-service на **Better Auth** (Drizzle-адаптер, D1): email/пароль, OAuth, верификация email, сброс пароля, секрет-хранилище сессий в KV; настройка cookie (httpOnly, Secure, SameSite), trustedOrigins, rate limit на auth-эндпоинты.
- JWT/JWKS-плагин: gateway проверяет токен локально по публичному ключу и пробрасывает контекст пользователя в сервисы (внутренние вызовы только через Service Bindings).
- Frontend: страницы login/register, Zod-формы, клиент Better Auth, защита роутов (Next middleware), Zustand только для UI-состояния сессии.
- **Тесты:** unit (конфиг, валидация), интеграционные (полный флоу, истёкшие/отозванные сессии, brute-force лимит), e2e (Playwright: регистрация → логин → выход).

### Этап 3. Workspaces и права (2 дня)

- workspace-service: CRUD, участники, роли, приглашения по ссылке.
- RBAC-проверки на уровне сервиса (не только gateway).
- Frontend: переключатель workspace, управление участниками (shadcn/ui).
- **Тесты:** матрица прав (роль × действие), параметризованные тесты.

### Этап 4. Страницы и дерево (3–4 дня)

- pages-service: вложенные страницы (parent_id + порядок через fractional indexing), перемещение, избранное, корзина.
- Frontend: сайдбар-дерево, drag&drop, оптимистичные обновления через TanStack Query (rollback при ошибке), prefetch на hover.
- **Тесты:** unit для алгоритма порядка и циклических перемещений, интеграционные для CRUD, компонентные тесты дерева.

### Этап 5. Блочный редактор (4–5 дней) — центр портфолио

- Блоки: текст, заголовки, списки, to-do, цитата, код (подсветка), divider, callout, изображение, toggle.
- Slash-меню, markdown-шорткаты, drag&drop блоков, автосохранение с debounce, Zustand для состояния редактора.
- Хранение: JSON-документ блоков; патчи/дебаунс-сохранение, версионирование (история изменений).
- **Тесты:** unit для сериализации/миграции схемы блоков, компонентные тесты, e2e основных сценариев редактирования.

### Этап 6. Медиа и файлы (2 дня)

- media-service: прямая загрузка в R2 (presigned URL), валидация типа/размера, обложки и иконки страниц, очистка сирот через Cron Trigger.
- Frontend: drag&drop загрузка, прогресс, превью.
- **Тесты:** мок R2 (Miniflare), контрактные тесты.

### Этап 7. Поиск (2 дня)

- search-service: D1 FTS5, индексация асинхронно через Queues (события page.updated/deleted).
- Frontend: Cmd+K палитра, дебаунс, подсветка совпадений.
- **Тесты:** индексация и ранжирование, идемпотентность консьюмера.

### Этап 8. Групповой realtime-воркспейс (4–5 дней)

- realtime-service: Durable Object на страницу, WebSocket (Hibernation API), Yjs-провайдер, awareness (курсоры и аватары участников), реконнект с догоном состояния.
- Интеграция с редактором: Tiptap Collaboration / BlockNote + Yjs; persistence — снапшоты Yjs-документа в pages-service (по таймеру и при пустой комнате), восстановление при холодном старте DO.
- Realtime-события воркспейса (появилась/удалена страница, изменились участники) — отдельный канал на workspace; инвалидация кеша TanStack Query по этим событиям.
- Права: проверка JWT при апгрейде, viewer не может писать, отзыв доступа закрывает соединение; лимиты на размер сообщения и частоту.
- **Тесты:** интеграционные тесты DO в vitest-pool-workers (два клиента → схождение состояния, реконнект, viewer не может писать), e2e Playwright с двумя браузерными контекстами.

### Этап 8.5. Шаринг и комментарии (2 дня)

- Публичные ссылки на страницы (read-only, отзываемые), комментарии к блокам и упоминания.
- **Тесты:** права доступа для публичных страниц, IDOR-проверки.

### Этап 9. Безопасность (сквозной этап, финальный аудит 2 дня)

Безопасность закладывается с этапа 0, а здесь выполняется аудит по чек-листу:

- **Аутентификация/сессии:** httpOnly+Secure+SameSite cookies, ротация и отзыв сессий, rate limit и lockout на логин/сброс пароля, одинаковые ответы при «нет такого пользователя/неверный пароль».
- **Авторизация:** deny-by-default, RBAC в каждом сервисе-владельце данных, проверка принадлежности ресурса workspace (защита от IDOR/BOLA), тесты матрицы прав.
- **Валидация:** Zod на каждом входе (body, query, params, WebSocket-сообщения, события Queues), лимиты размера, allowlist типов файлов.
- **Веб-защита:** CSP (nonce), HSTS, X-Content-Type-Options, Referrer-Policy, строгий CORS по allowlist, CSRF-защита, защита от XSS (санитизация контента редактора, безопасный рендер публичных страниц).
- **Файлы:** проверка MIME по содержимому, лимиты размера, приватный R2 + короткоживущие подписанные URL, раздача пользовательских файлов с отдельного домена, `Content-Disposition`/`nosniff`.
- **Межсервисная безопасность:** сервисы не имеют публичных маршрутов, доверяют только Service Bindings; контекст пользователя подписан/проверяем.
- **Секреты и зависимости:** секреты только через `wrangler secret`, нет секретов в репозитории (gitleaks), Dependabot/`pnpm audit`, SAST (CodeQL).
- **Приватность и аудит:** аудит-лог чувствительных действий (смена ролей, удаление, шаринг), удаление аккаунта и данных, нет PII в логах.
- **Тесты безопасности:** негативные тесты (чужой workspace, истёкшая сессия, viewer пишет, oversized payload, XSS-пейлоады), отдельные CI-проверки.

### Этап 10. Качество, наблюдаемость, DX (2–3 дня)

- OpenAPI из Hono (`@hono/zod-openapi`) + Scalar/Swagger UI.
- Структурное логирование, трейсинг request-id между сервисами, Sentry.
- Производительность: кеш в KV, `Cache-Control`/ETag, Lighthouse, bundle-анализ.
- Доступность (a11y), тёмная тема, адаптив, скелетоны, error boundaries.
- **Тесты:** покрытие ≥ 80% по сервисам и ключевым фронт-модулям, порог в CI.

### Этап 11. Деплой и презентация (1–2 дня)

- Деплой: Pages/Workers (vinext для Next.js на Cloudflare), окружения preview/prod, миграции в CI.
- README с диаграммой архитектуры (Mermaid), ADR, демо-аккаунт, GIF/видео, список компромиссов и «что улучшил бы».
- Seed демо-данных.

## Стратегия тестирования (пирамида)

- **Unit (Vitest):** чистая логика, Zod-схемы, утилиты, хуки.
- **Integration:** каждый воркер в `@cloudflare/vitest-pool-workers` с реальными D1/R2/KV-биндингами (Miniflare), включая Service Bindings.
- **Contract:** Zod-контракты из `packages/contracts` проверяются на обеих сторонах.
- **Component:** Testing Library + MSW.
- **E2E:** Playwright на ключевые сценарии (auth, создание страницы, редактирование, загрузка файла, поиск, совместное редактирование двумя пользователями).
- **Security:** негативные тесты авторизации (IDOR, роли), XSS-пейлоады, лимиты, rate limit; gitleaks, CodeQL, `pnpm audit` в CI.
- **CI-гейты:** lint, typecheck, тесты, порог покрытия, e2e на PR.

## О проекте
Клон Notion: рабочие пространства, вложенные страницы, блочный редактор, групповое редактирование в реальном времени, загрузка файлов, поиск, роли и шаринг. Безопасность — обязательное требование.

## Стек (строго)
Frontend:
- Next.js (App Router, TypeScript strict)
- TanStack Query (серверное состояние, оптимистичные обновления)
- Zustand (клиентское состояние, например состояние редактора)
- Zod (валидация форм и API, схемы общие с бэкендом)
- shadcn/ui + Tailwind
- Редактор: Tiptap или BlockNote, dnd-kit

Backend (микросервисы на Cloudflare Workers):
- Hono (+ @hono/zod-openapi, Hono RPC для типизированного клиента)
- Drizzle ORM + drizzle-kit (обязательно во всех сервисах, миграции в репозитории)
- Better Auth (Drizzle-адаптер, D1, KV secondary storage) в auth-service; JWT/JWKS для проверки токенов в gateway
- Сервисы: gateway, auth-service, workspace-service, pages-service, media-service, search-service, realtime-service (Durable Objects + Yjs, групповое редактирование в реальном времени)
- Связь между сервисами через Service Bindings; публично доступен только gateway
- Каждый сервис владеет своей базой Cloudflare D1 (database-per-service), общих таблиц между сервисами нет
- Cloudflare R2 — файлы; KV — кеш/rate limit; Queues — асинхронные события (индексация поиска); Cron Triggers — фоновая очистка

Инфраструктура и качество:
- Монорепо: pnpm workspaces + Turborepo (apps/web, services/*, packages/contracts, packages/config)
- Общие Zod-схемы и типы событий в packages/contracts
- Тесты: Vitest, @cloudflare/vitest-pool-workers (интеграционные тесты воркеров с реальными D1/R2/KV биндингами), Testing Library, MSW, Playwright (e2e). Целевое покрытие ≥ 80%
- CI: GitHub Actions (lint, typecheck, tests, coverage gate), деплой через Wrangler

## Принципы
1. Сначала контракты (Zod-схемы), потом реализация.
2. Слои в каждом сервисе: routes → service (бизнес-логика) → repository (Drizzle). Бизнес-логика не знает про HTTP.
3. Единый формат ошибок (RFC 7807), request-id сквозь все сервисы, структурные логи.
4. Авторизация (RBAC) проверяется в сервисе-владельце данных, а не только в gateway.
5. Никаких any, никаких «магических» строк; ошибки обрабатываются явно.
6. Каждая фича поставляется вместе с тестами. Нет тестов — задача не завершена.
7. Ключевые решения фиксируются в docs/adr/*.md.
8. Учитывай ограничения Workers: нет Node-API без совместимости, WebCrypto вместо нативных bcrypt/argon2, лимиты CPU/размера бандла, D1 — SQLite-семантика (FTS5, нет долгих транзакций).
9. Безопасность — требование первого класса, а не финальный этап: deny-by-default авторизация, RBAC и проверка принадлежности ресурса в каждом сервисе (защита от IDOR), Zod-валидация всех входов (включая WebSocket и Queues), httpOnly/Secure/SameSite cookies, строгий CORS, CSP и security-заголовки, rate limiting, санитизация контента редактора, приватный R2 с подписанными URL, секреты только через wrangler secret, нет PII в логах, аудит-лог чувствительных действий. Для каждой фичи добавляй негативные тесты безопасности (чужой workspace, viewer пишет, истёкшая сессия, XSS-пейлоад, oversized payload).
10. Для realtime: Yjs поверх Durable Objects (WebSocket Hibernation API), проверка токена при апгрейде соединения и роли на каждое сообщение, снапшоты документа в pages-service, реконнект с догоном состояния.

## Как работать со мной
- Работаем строго по этапам. Не переходи к следующему, пока я не подтвержу текущий.
- Перед каждым этапом: кратко опиши план (файлы, схемы, API-эндпоинты, тест-кейсы) и дождись моего «ок».
- После этапа: покажи структуру изменений, как запустить и как проверить, список тестов и покрытие.
