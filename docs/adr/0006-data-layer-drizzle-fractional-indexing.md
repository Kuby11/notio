# ADR 0006. Data layer: Drizzle, fractional indexing, UUIDv4

- **Status:** accepted
- **Date:** 2026-10-18

## Context

pages-service needs to store pages and blocks in D1: a tree with arbitrary ordering, soft
deletion, paginated output and, later (Stage 8), partial updates from a CRDT document. Ordering
within the tree is the key decision: it determines whether neighbouring rows have to be rewritten
on insert.

## Decision

### ORM and schema

**Drizzle ORM** (`drizzle-orm` + `drizzle-kit`), SQLite dialect. Reasons: type-safe queries,
migrations in the repository (plain SQL files, applicable with `wrangler d1 migrations apply`),
predictable behaviour with D1.

The table is per block, not one JSON document per page: row-level updates do not lock the whole
document, realtime partial patches are cheaper and version history is easier to compute.

```sql
pages(id, workspace_id, parent_id, title, icon, cover_file_id, position,
      is_favorite, is_trashed, created_by, created_at, updated_at)
blocks(id, page_id, type, position, content /* JSON */, created_at, updated_at)
```

Indexes match real queries: `(workspace_id, parent_id, position)` for the tree,
`(workspace_id, updated_at)` for lists. Time is stored as ISO-8601 in TEXT, booleans as INTEGER.

### Ordering within the tree

The **`fractional-indexing`** library (rocicorp, ~1 KB). A new page gets a position strictly
between its neighbours, so inserting in the middle does not rewrite other rows.

- without `afterPageId` the page becomes the last in the list;
- with `afterPageId` it goes right after the given neighbour;
- the pagination cursor is the `position` of the last item (a `gt(position)` comparison).

A custom implementation was rejected: key ordering correctness is not the logic worth writing and
rewriting in a project where it runs on both ends (writing and reading).

### Identifiers

**UUIDv4** in TEXT, generated by the service through WebCrypto (`newId()` in contracts).
ULID/UUIDv7 were rejected: the benefit (sortability) does not justify dropping a single,
widely accepted format — at this data volume index locality is not critical.

### Layers

```
routes (HTTP) → service (use cases, no HTTP) → repository (Drizzle) → D1
```

Domain errors (`NotFoundError`, `ForbiddenError`, `ConflictError`, `ValidationError`) are declared
in the service and turned into RFC 7807 by the app's error handler. A use case imports neither
Hono nor Response.

## Consequences

**Positive:**

- migrations are plain SQL in the repository, applied in tests and locally;
- a page from someone else's workspace answers 404 rather than 403: the response code cannot
  distinguish a foreign resource from a missing one (IDOR protection);
- data from the database is also validated by the `PageSchema` Zod schema — a "broken" row does
  not become a malformed object on the frontend.

**Negative:**

- position is a string, not a number: comparison is lexicographic only, and an arbitrary SQL
  `ORDER BY` on position must be kept in mind;
- `fractional-indexing` does not publish types, so a local declaration
  `src/types/fractional-indexing.d.ts` was added with a comment (no ADR needed — the scope is
  small).

## Alternatives

- **Integer order with renumbering** — simple, but inserting in the middle writes O(n) rows and
  conflicts under concurrent work.
- **LexoRank** — the same solution, but harder to implement.
- **One JSON document per page** — simpler whole-document writes, but partial updates are
  impossible and version history is expensive.
