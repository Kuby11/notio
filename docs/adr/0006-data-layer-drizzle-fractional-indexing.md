# ADR 0006. Слой данных: Drizzle, fractional indexing, UUIDv4

- **Статус:** принято
- **Дата:** 2026-10-18

## Контекст

pages-service нужно сохранять страницы и блоки в D1: дерево с произвольным порядком,
мягкое удаление, постраничная выдача и, позже (Этап 8), частичные обновления от
CRDT-документа. Порядок в дереве — ключевое решение: от него зависит, придётся ли
переписывать соседние строки при вставке.

## Решение

### ORM и схема

**Drizzle ORM** (`drizzle-orm` + `drizzle-kit`), диалект SQLite. Причины: типобезопасные
запросы, миграции в репозитории (обычные SQL-файлы, применимые `wrangler d1 migrations apply`),
предсказуемая работа с D1.

Таблица — на блок, а не один JSON-документ на страницу: построчные обновления
не блокируют весь документ, дешевле частичные патчи от realtime и проще считать
историю версий.

```sql
pages(id, workspace_id, parent_id, title, icon, cover_file_id, position,
      is_favorite, is_trashed, created_by, created_at, updated_at)
blocks(id, page_id, type, position, content /* JSON */, created_at, updated_at)
```

Индексы под реальные запросы: `(workspace_id, parent_id, position)` — дерево,
`(workspace_id, updated_at)` — списки. Время хранится ISO-8601 в TEXT, булевы — INTEGER.

### Порядок в дереве

Библиотека **`fractional-indexing`** (rocicorp, ~1 КБ). Новая страница получает
позицию строго между соседями, поэтому вставка в середину не переписывает другие строки.

- без `afterPageId` страница становится последней в списке;
- с `afterPageId` встаёт сразу после указанной соседней;
- курсор постраничной выдачи — это `position` последнего элемента (сравнение `gt(position)`).

Своя реализация отклонена: корректность порядка ключей — не та логика, которую стоит
писать и переписывать в проекте, где она работает на обоих концах (запись и выборка).

### Идентификаторы

**UUIDv4** в TEXT, генерируется сервисом через WebCrypto (`newId()` в контрактах).
Отклонены ULID/UUIDv7: преимущество (сортируемость) не окупает отказ от единого,
общепринятого формата — при таком объёме данных locality индекса не критична.

### Слои

```
routes (HTTP) → service (сценарии, без HTTP) → repository (Drizzle) → D1
```

Доменные ошибки (`NotFoundError`, `ForbiddenError`, `ConflictError`, `ValidationError`)
объявлены в сервисе и превращаются в RFC 7807 в обработчике ошибок приложения.
Сценарий не импортирует ни Hono, ни Response.

## Последствия

**Положительные:**

- миграции — обычные SQL в репозитории, применяются и в тестах, и локально;
- страница чужого workspace отвечает 404, а не 403: по коду ответа нельзя
  отличить чужой ресурс от несуществующего (защита от IDOR);
- данные из базы тоже валидируются Zod-схемой `PageSchema` — «сломанная» строка
  не превращается в кривой объект на фронтенде.

**Отрицательные:**

- позиция — строка, а не число: сравнение только лексикографическое, произвольный
  SQL-ORDER BY по position нужно помнить;
- `fractional-indexing` не публикует типы, добавлена локальная декларация
  `src/types/fractional-indexing.d.ts` с комментарием (ADR 0012 не нужен — объём мал).

## Альтернативы

- **Целочисленный порядок с пересчётом** — просто, но вставка в середину пишет
  O(n) строк и конфликтует при параллельной работе.
- **LexoRank** — то же решение, но сложнее в реализации.
- **Один JSON-документ на страницу** — проще запись целиком, но невозможны
  частичные обновления и дорогая история версий.
