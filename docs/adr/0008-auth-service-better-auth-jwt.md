# ADR 0008. Аутентификация: Better Auth, сессия в cookie и JWT для gateway

- **Статус:** принято
- **Дата:** 2026-10-18

## Контекст

До Этапа 2 идентичность пользователя в dev передавалась заголовком `x-actor-id`,
который принимал gateway. Заголовок, который клиент задаёт сам, — это не
аутентификация: любой, кто достучался до gateway, объявлял себя кем угодно.
Нужна настоящая аутентификация с тремя требованиями:

1. браузер хранит сессию в httpOnly-cookie, токен не доступен скриптам страницы;
2. gateway проверяет права без похода в auth-service на каждый запрос;
3. закрытые маршруты API отвечают единым форматом ошибок проекта (RFC 7807).

## Решение

### Отдельный сервис `auth-service`

Аутентификация изолирована в отдельном воркере со своей базой `notio-auth`:
table-per-service, наружу сервис не выставлен, gateway обращается к нему только
через Service Binding. Схема (`user`, `session`, `account`, `verification`, `jwks`)
генерируется официальным `@better-auth/cli generate` и не редактируется руками.

### Drizzle-адаптер, а не нативный D1

Схема, сгенерированная CLI, хранит поля в `snake_case` и рассчитана на
Drizzle-адаптер. Нативный D1-адаптер Better Auth ожидает `camelCase`-колонки и
отвергает такую схему при старте. Поэтому `database: drizzleAdapter(createDb(env, authSchema), …)`
и общая с pages-service кодовая база `@notio/db`.

### Сессия — cookie, доступ к API — JWT

- Браузер получает `notio.session_token` (httpOnly, `SameSite=Lax`, Secure в production).
- `POST /api/auth/sign-up/email` требует подтверждения почты; ссылка — подписанный
  JWT, поэтому таблица `verification` остаётся пустой, а токен нельзя перебрать в базе.
- Для вызовов закрытого API клиент берёт короткоживущий JWT (`GET /api/auth/token`).
  Он передаётся в заголовке `Authorization: Bearer` и не сохраняется ни в
  `localStorage`, ни в Zustand.
- **Cookie-кэш Better Auth отключён.** С ним кэшированные данные сессии продолжали
  отдавать пользователя несколько минут после выхода из аккаунта. Чтение сессии из
  D1 локально и дешевле, чем эта ошибка.

### Gateway проверяет подпись локально

`authenticationMiddleware` берёт JWKS у auth-service через Service Binding, кеширует
его в памяти изолята (`jwks.ts`, TTL из `AUTH_JWKS_CACHE_TTL_SECONDS`) и проверяет
подпись через `jose`. Ни один запрос к `/api/pages` не превращается во внутренний
вызов. Заголовки `x-user-id`/`x-actor-id` от клиента отбрасываются, сервис получает
идентичность только из проверенных claims (`x-actor-id`, ставится gateway'ом).

Публичные пути: `/`, `/health`, `/api/health`, `/api/auth/*`. Остальное под
`/api/*` без валидного токена — `401 application/problem+json` с кодом `UNAUTHENTICATED`.

### Повторная регистрация закрыта нами, а не библиотекой

Better Auth 1.7 отвечает на повторную регистрацию того же email кодом 200 и возвращает
пользователя, которого в базе нет: вставка нарушила уникальный индекс, а ошибка не
поднялась до клиента. Пользователь увидел бы «аккаунт создан» и потерял бы его.
Поэтому `POST /api/auth/sign-up/email` в auth-service сначала проверяет занятость почты
(`src/db/user.repository.ts`) и отвечает `409 CONFLICT` в общем формате ошибок проекта.
Логика Better Auth при этом не переписывается — проверка живёт в отдельном слое маршрута.

### Письма — через порт `MailSender`

Сервис не знает про SMTP и провайдеров: `MailSender` — порт с полями «получатель,
тема, ссылка действия». В dev реализация пишет письмо в лог (ссылка видна и
используется скриптом `pnpm smoke`), в production заглушка честно падает, чтобы
не сообщить об успешной отправке письма, которое никто не получит. Провайдер
(Cloudflare Email Sending, Resend) подключается в composition root.

### OAuth-ключи включают провайдер

Провайдеры GitHub и Google подключены, но активируются только при наличии пары
`CLIENT_ID`/`CLIENT_SECRET` в секретах: без них Better Auth не предлагает вход,
который невозможно завершить.

## Альтернативы

- **Сессионная проверка в gateway через вызов auth-service на каждый запрос.**
  Отброшена: добавляет зависимость и задержку ко всем запросам API ради проверки,
  которую можно сделать локально по подписи.
- **Хранить JWT в localStorage.** Отброшено: доступен скриптам страницы, уязвим к XSS.
- **Нативный D1-адаптер Better Auth с ручными camelCase-колонками.** Отброшено:
  схема вручную расходится с той, что генерирует CLI, и ломается при обновлении.
- **Собственная реализация паролей и сессий.** Отброшено: пароли, ротация ключей,
  CSRF и лимиты — не та логика, которую нужно писать вручную.

## Последствия

- Идентификаторы Better Auth генерируются как UUID (`advanced.database.generateId`):
  внутренние сервисы принимают только UUID из общего контракта.
- Лимиты Better Auth считаются по `cf-connecting-ip`, который проставляет Cloudflare;
  доверять заголовкам клиента нельзя.
- Счётчики rate limit Better Auth живут в KV. В KV нет атомарного инкремента, поэтому
  параллельные запросы одного клиента могут проскочить счётчик на единицу — тот же
  компромисс, что и в rate limit gateway. Для строгого лимита нужен Durable Object.
- Фронтенд ходит в Better Auth через клиент `createAuthClient`, но ответы
  перепроверяет Zod-схемами на границе адаптера: сеть не считается доверенной.
