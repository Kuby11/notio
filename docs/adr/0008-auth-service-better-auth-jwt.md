# ADR 0008. Authentication: Better Auth, cookie session and JWT for the gateway

- **Status:** accepted
- **Date:** 2026-10-18

## Context

Before Stage 2 the user's identity in dev was passed in an `x-actor-id` header that the gateway
accepted. A header the client sets itself is not authentication: anyone who reached the gateway
could claim to be anyone. Real authentication is needed, with three requirements:

1. the browser keeps the session in an httpOnly cookie, with the token unavailable to page scripts;
2. the gateway verifies permissions without calling auth-service on every request;
3. private API routes answer with the project's single error format (RFC 7807).

## Decision

### A separate `auth-service`

Authentication is isolated in its own worker with its own `notio-auth` database: table-per-service,
the service is not exposed publicly, and the gateway reaches it only through a Service Binding.
The schema (`user`, `session`, `account`, `verification`, `jwks`) is generated by the official
`@better-auth/cli generate` and is not edited by hand.

### Drizzle adapter, not native D1

The schema generated by the CLI stores fields in `snake_case` and is designed for the Drizzle
adapter. Better Auth's native D1 adapter expects `camelCase` columns and rejects such a schema at
startup. Hence `database: drizzleAdapter(createDb(env, authSchema), …)` and the shared
`@notio/db` codebase with pages-service.

### Session is a cookie, API access is a JWT

- The browser receives `notio.session_token` (httpOnly, `SameSite=Lax`, Secure in production).
- `POST /api/auth/sign-up/email` requires email verification; the link is a signed JWT, so the
  `verification` table stays empty and the token cannot be brute-forced from the database.
- For private API calls the client takes a short-lived JWT (`GET /api/auth/token`). It is sent in
  the `Authorization: Bearer` header and is stored neither in `localStorage` nor in Zustand.
- **Better Auth's cookie cache is disabled.** With it, cached session data kept returning the user
  for several minutes after signing out. Reading the session from D1 is locally cheaper than that
  bug.

### The gateway verifies the signature locally

`authenticationMiddleware` fetches JWKS from auth-service through the Service Binding, caches it in
isolate memory (`jwks.ts`, TTL from `AUTH_JWKS_CACHE_TTL_SECONDS`) and verifies the signature via
`jose`. No request to `/api/pages` turns into an internal call. Client-supplied `x-user-id` /
`x-actor-id` headers are discarded; the service receives identity only from verified claims
(`x-actor-id`, set by the gateway).

Public paths: `/`, `/health`, `/api/health`, `/api/auth/*`. Everything else under `/api/*` without
a valid token gets `401 application/problem+json` with the `UNAUTHENTICATED` code.

### Duplicate sign-up is closed by us, not by the library

Better Auth 1.7 answers a duplicate sign-up for the same email with status 200 and returns a user
that does not exist in the database: the insert violated the unique index and the error never
surfaced to the client. The user would see "account created" and lose it. Therefore
`POST /api/auth/sign-up/email` in auth-service first checks whether the email is taken
(`src/db/user.repository.ts`) and answers `409 CONFLICT` in the project's shared error format.
Better Auth's logic is not rewritten — the check lives in a separate route layer.

### Email through the `MailSender` port

The service knows nothing about SMTP or providers: `MailSender` is a port with "recipient, subject,
action link" fields. In dev the implementation writes the email to the log (the link is visible and
used by the `pnpm smoke` script), while in production the stub fails honestly, so it never reports
a successful send that nobody would receive. A provider (Cloudflare Email Sending, Resend) is wired
in the composition root.

### OAuth keys enable a provider

GitHub and Google providers are wired, but activate only when a `CLIENT_ID`/`CLIENT_SECRET` pair is
present in the secrets: without them Better Auth does not offer a sign-in that cannot be completed.

## Alternatives

- **Session check in the gateway via a call to auth-service on every request.** Rejected: adds a
  dependency and latency to every API request for a check that can be done locally from the
  signature.
- **Storing the JWT in localStorage.** Rejected: reachable by page scripts, vulnerable to XSS.
- **Better Auth's native D1 adapter with hand-written camelCase columns.** Rejected: the schema
  drifts from what the CLI generates and breaks on upgrade.
- **A custom implementation of passwords and sessions.** Rejected: passwords, key rotation, CSRF
  and limits are not logic to write by hand.

## Consequences

- Better Auth identifiers are generated as UUIDs (`advanced.database.generateId`): internal services
  accept only UUIDs from the shared contract.
- Better Auth limits are counted by `cf-connecting-ip`, which Cloudflare sets; client headers
  cannot be trusted.
- Better Auth rate-limit counters live in KV. KV has no atomic increment, so concurrent requests
  from one client can slip past the counter by one — the same trade-off as in the gateway rate
  limit. A strict limit needs a Durable Object.
- The frontend talks to Better Auth through the `createAuthClient` client, but re-checks responses
  with Zod schemas at the adapter boundary: the network is not considered trusted.
